# Alembic Database Migrations

This directory contains `apps/cloud-api`'s Alembic migration history. It is scoped
to this app only — `apps/desktop/engine` persists locally in SQLite and has no
Alembic setup (see [`apps/desktop/README.md`](../../desktop/README.md)); the shared
[`packages/ntk-core`](../../../packages/ntk-core) library has no database at all.

SQLModel (`api.models.sql`, see [`apps/cloud-api/README.md`](../README.md)) defines
the current application schema. Alembic defines how an existing PostgreSQL database
moves from one schema version to another. All commands below run from inside
`apps/cloud-api` (where `alembic.ini` lives):

```bash
cd apps/cloud-api
uv run alembic <command>
```

## Structure

```text
alembic/
├── env.py
├── script.py.mako
├── README.md
└── versions/
    ├── <YYYYDDMM_NNNN_description>.py
    └── ...
```

Migration filenames use:

```text
YYYYMMDD_NNNN_description.py
```

Alembic determines migration order from the `revision` and `down_revision` values inside each migration file, not from the filename.

## Creating a Migration

After changing a SQLModel table:

```bash
alembic revision --autogenerate -m "describe the schema change"
```

Review the generated migration before applying it.

Autogenerate may not correctly understand:

- column or table renames
- data migrations
- destructive changes
- nullable changes
- foreign keys
- unique constraints
- indexes
- enum changes

Never assume an autogenerated migration is correct.

## Applying Migrations

Apply all pending migrations:

```bash
alembic upgrade head
```

Check the current database revision:

```bash
alembic current
```

View migration history:

```bash
alembic history
```

View migration heads:

```bash
alembic heads
```

Apply only the next migration:

```bash
alembic upgrade +1
```

Roll back one migration:

```bash
alembic downgrade -1
```

Only downgrade when the migration is safely reversible.

## Existing (Pre-Split) Database

Migration history before `20260915_0000` tracked a single, unified schema that
included `person`/clinical tables alongside NCP tables. That schema predates the
cloud/desktop split (see the root [README.md](../../../README.md#architecture)):
person/clinical data now lives entirely on-device in `apps/desktop/engine`'s
SQLite database, never in this Postgres database, so those old migrations were
retired rather than carried forward — `20260915_0000` is a fresh baseline that
creates only the tables `api.models.sql` currently declares.

If you have an existing database that still has `person`/`person_*` tables from
before the split, it is **not** upgradable in place — that data does not belong in
this schema anymore and there is no migration path that trims it in place.
Instead:

1. If the `person`/clinical data in it is worth keeping, export it before doing
   anything else (there is no automated tool for moving it into engine's SQLite
   database yet).
2. Drop and recreate the database, then run `alembic upgrade head` as described
   under [New Database](#new-database) below.

## New Database

For a new empty database, do not stamp it.

Run:

```bash
alembic upgrade head
```

The complete database schema should be reproducible from the Alembic migration history.
The baseline enables PostgreSQL's `vector` extension before it creates any
pgvector columns or indexes, so the migration role must have permission to
enable that extension.

## Required Columns and Data Backfills

When adding a required column to a table containing existing data, use a staged migration when necessary.

For example:

```text
1. Add observed_at as nullable
2. Backfill it from a reliable source timestamp
3. Verify remaining NULL values
4. Make observed_at NOT NULL
```

Do not invent data solely to satisfy a database constraint.

## Destructive Changes

Be especially careful with:

- `DROP TABLE`
- `DROP COLUMN`
- nullable → non-nullable changes
- type changes
- removed foreign keys
- removed unique constraints

Preserve or migrate required data before removing the old schema.

## Migration Rules

- Keep migrations small and focused.
- Use Alembic for all persisted schema changes.
- Review autogenerated migrations.
- Do not import current application SQLModel classes into historical migration files.
- Historical migrations must remain executable as application models evolve.
- Include meaningful `downgrade()` logic when reversal is safe.
- Do not pretend destructive migrations are reversible when deleted data cannot be restored.
- Do not use `SQLModel.metadata.create_all()` as a substitute for migrations in deployed environments.

## Development Workflow

```text
Change SQLModel model
        ↓
Generate Alembic revision
        ↓
Review/edit migration
        ↓
Run tests
        ↓
alembic upgrade head
        ↓
Run application
```

## Deployment

Migrations should eventually run as an explicit deployment step:

```text
Build application
        ↓
Run migration job
        ↓
alembic upgrade head
        ↓
Start/deploy application
```

Do not have every FastAPI process independently run database migrations during startup.

The migrations should remain compatible with standard PostgreSQL whether hosted locally, in Docker, Supabase, AWS RDS, or another PostgreSQL provider.
