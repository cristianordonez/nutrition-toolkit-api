# Alembic Database Migrations

This directory contains the project's Alembic migration history.

SQLModel defines the current application schema. Alembic defines how an existing PostgreSQL database moves from one schema version to another.

## Structure

```text
alembic/
├── env.py
├── script.py.mako
├── README.md
└── versions/
    ├── <YYYYDDMM_NNNN_>.py
    └── ...
```

Migration filenames use:

```text
YYYYMMDD_NNNN_description.py
```

Alembic determines migration order from the `revision` and `down_revision` values inside each migration file, not from the filename.

## Creating a Migration

After changing a SQLModel table:

```bash
alembic revision --autogenerate -m "describe the schema change"
```

Review the generated migration before applying it.

Autogenerate may not correctly understand:

- column or table renames
- data migrations
- destructive changes
- nullable changes
- foreign keys
- unique constraints
- indexes
- enum changes

Never assume an autogenerated migration is correct.

## Applying Migrations

Apply all pending migrations:

```bash
alembic upgrade head
```

Check the current database revision:

```bash
alembic current
```

View migration history:

```bash
alembic history
```

View migration heads:

```bash
alembic heads
```

Apply only the next migration:

```bash
alembic upgrade +1
```

Roll back one migration:

```bash
alembic downgrade -1
```

Only downgrade when the migration is safely reversible.

## Existing Database

If an existing database already matches the baseline represented by:

```text
20260904_0001
```

initialize Alembic tracking with:

```bash
alembic stamp 20260904_0001
```

Then run:

```bash
alembic upgrade head
```

`stamp` does not execute schema changes. It only tells Alembic that the database should be considered to already be at that revision.

Only stamp a database after verifying that its schema actually matches the baseline.

## New Database

For a new empty database, do not stamp it.

Run:

```bash
alembic upgrade head
```

The complete database schema should be reproducible from the Alembic migration history.

## Required Columns and Data Backfills

When adding a required column to a table containing existing data, use a staged migration when necessary.

For example:

```text
1. Add observed_at as nullable
2. Backfill it from a reliable source timestamp
3. Verify remaining NULL values
4. Make observed_at NOT NULL
```

Do not invent data solely to satisfy a database constraint.

## Destructive Changes

Be especially careful with:

- `DROP TABLE`
- `DROP COLUMN`
- nullable → non-nullable changes
- type changes
- removed foreign keys
- removed unique constraints

Preserve or migrate required data before removing the old schema.

## Migration Rules

- Keep migrations small and focused.
- Use Alembic for all persisted schema changes.
- Review autogenerated migrations.
- Do not import current application SQLModel classes into historical migration files.
- Historical migrations must remain executable as application models evolve.
- Include meaningful `downgrade()` logic when reversal is safe.
- Do not pretend destructive migrations are reversible when deleted data cannot be restored.
- Do not use `SQLModel.metadata.create_all()` as a substitute for migrations in deployed environments.

## Development Workflow

```text
Change SQLModel model
        ↓
Generate Alembic revision
        ↓
Review/edit migration
        ↓
Run tests
        ↓
alembic upgrade head
        ↓
Run application
```

## Deployment

Migrations should eventually run as an explicit deployment step:

```text
Build application
        ↓
Run migration job
        ↓
alembic upgrade head
        ↓
Start/deploy application
```

Do not have every FastAPI process independently run database migrations during startup.

The migrations should remain compatible with standard PostgreSQL whether hosted locally, in Docker, Supabase, AWS RDS, or another PostgreSQL provider.
